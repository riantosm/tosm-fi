# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # start Vite dev server (port 5173, or $PORT)
npm run build     # tsc -b (type-check via project references) then vite build
npm run lint      # eslint .
npm run preview   # preview the production build
```

There is no test suite/framework configured in this project.

## Architecture

TosmFi is a React 19 + TypeScript + Vite money-tracking app. **Auth, wallet, category, transaction, report, and investment (instrument + investment transaction ledger) are wired to a real backend; settings is still mocked.** All non-backed data lives in Redux (persisted to `localStorage` via `redux-persist`), and every "API call" for those entities is a service function that awaits a fake `delay()` and returns/mutates mock data (seeded from empty arrays in `src/constants/mock-*.ts` — deliberately emptied, not deleted, so the seam stays obvious for whoever builds the real backend next). `src/constants/api-docs.ts` is not just documentation — it's the living spec of every endpoint the mock layer already emulates (or, for the "auth", "wallet", "category", and "transaction" groups, the real contract already implemented), rendered at Settings → Backend API for whoever builds the rest of the real backend later. Report is real too but has **no dedicated backend endpoints of its own** — see "Report (real, composed from the transaction API)" below — so its api-docs.ts group stays as an unbuilt aspirational spec, not the real contract.

### Real backend integration (auth + wallet + category + transaction)

The sibling repo `../tosm-fi-be` (Express/Mongoose, see its own `CLAUDE.md`) implements `/auth/{register,login,logout}`, `/user/{me,get-list-user,accept-user}`, `/wallets/{"", ":idWallet", ":idWallet/primary", "reorder"}`, `/categories/{...}`, and `/transactions/{"", ":idTransaction"}` (see below) for real, at `http://localhost:3000/api`. Nothing else (settings) has a real backend yet — don't assume the pattern below extends to it until it's actually built. Report doesn't have its own backend routes either, but gets real data by composing calls to the transaction endpoint below — see the dedicated section further down.

- `src/services/wallet.service.ts`, `src/services/category.service.ts`, and `src/services/transaction.service.ts` call the real endpoints the same way `auth.service.ts` does (try/catch around `httpClient`, `getApiErrorMessage` for the error message) — no `delay()`, no mock array. `useWallets()`/`useCategories()`/`useTransactions()` didn't need to change shape at all: they still just compose service + slice, same as every mocked entity's hook.
- Category's backend embeds subcategories directly in the category document (not a separate collection) — matches the FE's nested `Category.subCategories: SubCategory[]` shape exactly, and means deleting a category cascades to its subcategories for free. Reorder endpoints exist at both levels: `/categories/reorder` (categories among themselves) and `/categories/:idCategory/subcategories/reorder` (subcategories within one category).
- `balance`/`transactionCount` (wallet) and `transactionCount` (category/subcategory) are owned by their respective backends but are **only ever mutated by the transaction backend**, atomically, inside the same Mongoose session transaction as the transaction write itself — see `tosm-fi-be`'s `transaction.service.ts` and its `CLAUDE.md` "Transaction domain" section. Because the backend now owns this, `src/hooks/use-transactions.ts` no longer computes wallet/category deltas client-side (that logic — `getWalletDeltas`/`accumulateWalletDeltas`/`buildWalletUpdate`/`buildCategoryUpdate` — was removed); it just calls `loadWallets()`/`loadCategories()` again after any create/edit/delete to resync the now-authoritative numbers from the server.
- `GET /transactions` always returns a `summary` alongside `transactions` — `{ income, expense, net, categoryBreakdown }`, aggregated server-side (Mongo `$group`) over the *entire* filtered set (every query param except `page`/`limit`), never just the current page. `categoryBreakdown` nests each expense category's own `subCategoryBreakdown`. This is what feeds `TransactionSummaryBar` (Transactions page), `CategoryBreakdownChart` (Dashboard, via `ExpenseByCategoryChart`), and Reports' own category-breakdown chart — none of them reduce a raw transaction array anymore. `CategoryBreakdownChart` is purely presentational (takes a `slices: CategorySlice[]` prop); `src/utils/category-breakdown.ts`'s `buildCategoryBreakdown(items: TransactionCategoryBreakdown[])` adapts the backend's nested shape into `CategorySlice[]` and is shared by both Dashboard and Reports.
- `transaction.service.ts` has a single read path, `queryTransactions(params)` → `GET /transactions` (all params optional; omitting `page`/`limit` returns the whole filtered set unpaginated with `page/limit/totalPages: null`; `type` filters by `income|expense|transfer|correction`). Every consumer fetches only the scoped window it needs into its own local component/hook state — results never touch the global slice. `TransactionsPage` queries filtered/sorted/paginated; `DashboardPage` queries just the current month; `use-reports.ts` queries an unpaginated window scoped tightly to just the resolved report period (see "Report" section below for how it avoids fetching more than that). **Nothing fetches the entire unpaginated history anymore** — the old `fetchTransactions()`/`loadTransactions()` full-history path was removed deliberately to save bandwidth; don't reintroduce it, transaction volume only grows over time. The `transaction` Redux slice still exists but purely as an app-wide mutation signal: its array is fed solely by `add/update/removeTransaction` after create/edit/delete, is never seeded from the server, has no `status` field, and is not persisted.
- `TransactionsPage` resets its `page` state to `1` whenever its filters change **or** whenever the global `transactions` array reference changes (i.e. after any create/edit/delete anywhere in the app) — so its accumulated list can never go stale or duplicate after a mutation. The reset happens by adjusting state **during render** (the `prevFilterKey`/`prevTransactions` state pair), not in an effect, so the query effect only ever sees the final page — no wasted intermediate request; a `refreshToken` baked into `queryKey` forces the refetch even when the page is already `1`. `DashboardPage` uses the same `transactions`-reference-as-change-signal trick (its own effect is keyed on `[queryTransactions, transactions]`) even though it never renders that array directly. Pagination itself is infinite scroll, not a button — an `IntersectionObserver` on a sentinel `<div>` at the bottom of the list advances `page` once it's within `200px` of the viewport.

- `src/services/http-client.ts` — a single axios instance every real call goes through. Its request interceptor attaches `Authorization: Bearer <token>` from the Redux store automatically; its response interceptor watches for `401` and, **only if the session was already logged in** (not a wrong-password 401 from the login call itself), dispatches `onSessionExpired()` — auto-logout on an invalid/expired/revoked token, with no explicit call site needed anywhere else.
- `src/services/auth.service.ts` calls the real endpoints. `src/hooks/use-auth.ts`'s `login()` calls `authService.login()` then immediately `authService.getMe()` — `onLogin` only dispatches if **both** succeed. This is what blocks a not-yet-approved (`pending`) user: login succeeds and returns a token, but `/user/me` 403s with "Menunggu validasi", so the user is never actually signed in even though a token exists momentarily.
- `authenticationSlice` has a `sessionExpired` flag, distinct from a normal `onLogout` — set only by the interceptor's auto-logout path. `LoginForm` reads it once, shows it as the existing red error banner ("Sesi kamu telah berakhir..."), then dismisses it via `onDismissSessionExpired` so it doesn't reappear on a later visit.
- `logout()` calls the real `/auth/logout` best-effort (wrapped in try/catch) and always clears local state in a `finally` — a dead token or network error should never trap the user in a logged-in-looking-but-broken state.
- `AuthUser` fields are camelCase matching the backend exactly: `idUser`, `nameUser`, `username`, `role`, `status`. `netWorth` is optional and currently always absent — the backend doesn't compute it (that's a wallet-aggregation concern, not implemented yet); `Topbar` already falls back to `?? 0`.
- The backend's response envelope is `{ message, data, isSuccess, status }` (not `{ success, ... }`) — reflected in `api-docs.ts`'s "auth", "wallet", "category", "transaction", "investment", and "investmentTransaction" group examples specifically, since those groups are real now. Every *other* group in that file still shows the old mock's `{ success, ... }` shape on purpose — don't "fix" those to match until their backend actually exists, and don't copy the real envelope into a new mocked entity either. (The "report" group is the odd one out — real data, but no real endpoints of its own; see below.)

### Investment domain (real backend — instrument + investment transaction ledger)

The Investment page (`src/app/pages/InvestmentPage`) was originally built fully mocked (in-memory + localStorage in `instrument.service.ts`); it's wired to the real backend now, mirroring category's embedded-subdocument pattern plus transaction's session-transaction pattern.

- `Instrument.investmentAccounts` is an **embedded** subdocument array on the backend (`tosm-fi-be`'s `instrument.model.ts`), not a separate collection — same reasoning as `Category.subCategories`: an investment account never exists outside its instrument, so deleting an instrument cascades to its accounts for free. `src/services/instrument.service.ts` calls the real endpoints (`GET/POST /instruments`, `PATCH/DELETE /instruments/:idInstrument`, and the three `/instruments/:idInstrument/accounts...` routes) the same way `category.service.ts` does — try/catch + `getApiErrorMessage`, no `delay()`, no mock array.
- `InvestmentTransaction` is a separate ledger collection (own service/hook: `src/services/investment-transaction.service.ts` / `src/hooks/use-investment-transactions.ts`), one document per operation (`type: "in" | "out" | "transfer" | "pl"`). Each entry stores `investedDelta`/`currentDelta` **explicitly** — the actual signed delta applied to the account's `investedAmount`/`currentValue` at creation time — rather than deriving it from `amount`+`type`, so edit/delete can reverse an entry exactly without re-deriving type-specific sign/cap logic.
- Money leaving an account (withdrawal, or a transfer's source side) is capped by `currentValue` (market value), not `investedAmount` (contributed principal) — a pure P/L gain (`investedAmount` 0, `currentValue` > 0) must still be fully cashable. `investedAmount` itself is only ever floored at 0, never driven negative. This is `computeOutgoingDelta` in the backend's `investment-transaction.service.ts` (ported 1:1 from the original mocked version).
- Edits/deletes reverse against the account's **current live totals**, not a true historical replay — if a later transaction already relied on what an earlier entry contributed, undoing the earlier one would drive the balance negative. Both the backend service and (formerly) the mock reject this case outright ("Tidak bisa menghapus/diperbarui, transaksi lain setelahnya bergantung pada perubahan ini") rather than silently corrupting the balance.
- `investmentAccounts[].investedAmount`/`currentValue` are only ever mutated by the investment-transaction backend, atomically, inside the same Mongoose session transaction as the ledger row write itself — same ownership pattern as wallet `balance`/category `transactionCount` being owned exclusively by the transaction backend. `use-investment-transactions.ts` no longer receives instrument deltas back from its mutation calls; each mutation calls `loadInstruments()` again afterward to resync from the server, matching `use-transactions.ts`'s `loadWallets()`/`loadCategories()` resync convention exactly.
- **Bidirectional cascade delete** between a wallet transaction and its linked investment ledger row (a "Catat sebagai Investasi" checkbox on `AddTransactionModal` links the two via `InvestmentTransaction.idTransaction`): deleting either side deletes the other, atomically, in the same DB transaction. Implemented via a deliberate circular import between `tosm-fi-be`'s `transaction.service.ts` and `investment-transaction.service.ts` — each exports a `removeCore`/session-accepting helper alongside its normal session-owning public `remove()`, and each public `remove()` calls the other domain's core helper inside its own session. Safe specifically because every cross-reference is invoked inside an async function body at request time, long after both modules have finished loading.
- `instrumentSlice` is persisted (added back to `store.ts`'s whitelist with the same `createResetStatusOnRehydrateTransform` treatment as wallet/category) now that it's backed by a real API. `investmentTransactionSlice` stays unpersisted — same reasoning as the `transaction` slice: a growing ledger, always freshly fetched, never worth persisting.
- `api-docs.ts`'s "investment" and "investmentTransaction" groups now show the real `{isSuccess}` envelope (previously the mock's `{success}` shape).

### Report (real dedicated endpoints — no more composing from the transaction API)

`src/services/report.service.ts` and `src/hooks/use-reports.ts` get real data from five dedicated `/reports/*` backend endpoints. This started as "compose everything from `GET /transactions`" (still true for `TransactionsPage`/`DashboardPage`), but every report widget outgrew that: summary needed 2 calls, wallet usage needed one call per wallet, cash flow needed the whole period's itemized transaction list shipped to the client just to bucket it, monthly trend needed one call per month. Each got its own endpoint instead once composing them meant too many round trips or too much payload.

- `reportService.fetchSummary(dateFrom, dateTo, previousDateFrom, previousDateTo)` → `GET /reports/summary` — one call. The backend computes **both** the current and previous period's `computeSummary()` (income/expense/categoryBreakdown/count) and the `changePercent` comparison server-side (`ReportService.getSummary` in `tosm-fi-be`, reusing the same `computeSummary()`/`buildDateFilter()` that power `GET /transactions`, now exported for this reuse). Splits the response into `{ summary, categoryBreakdown }` client-side — `categoryBreakdown` isn't part of the `ReportSummary` type since `ReportSummaryCards` doesn't need it.
- `reportService.fetchWalletUsage(dateFrom, dateTo)` → `GET /reports/wallet-usage` — one call, one Mongo aggregation grouping every wallet at once (`$filter` down to `[idWallet, idWalletFrom, idWalletTo]` per transaction, `$unwind` + `$group`) instead of one `queryTransactions` call per wallet. Names/colors are resolved server-side, so the frontend no longer needs `wallets` for this call.
- `reportService.fetchTopSpending(dateFrom, dateTo, limit)` → `GET /reports/top-spending` — one call (`type=expense` filter added to the backend's transaction query builder specifically to make this endpoint possible); category/subcategory names are resolved server-side, so the frontend no longer needs `categories` for this call either.
- `reportService.fetchCashFlow(dateFrom, dateTo, locale)` → `GET /reports/cash-flow` — one call. `ReportService.getCashFlow` buckets by hour/day/week/month server-side via `buildReportBuckets()` in `tosm-fi-be`'s `src/utils/reportBuckets.ts` — ported 1:1 from the frontend's old client-side bucketing (which is why the frontend's own `buildReportBuckets`/`ReportBucket`/`HOUR_BLOCK_STARTS` in `src/utils/report-period.ts` were deleted as dead code). Anchored in UTC (`Date.UTC`/`getUTC*`) to match how `buildDateFilter()` already interprets `dateFrom`/`dateTo` query params — bucket boundaries must tile exactly inside that same window.
- `reportService.fetchMonthlyTrend(monthsCount, locale)` → `GET /reports/monthly-trend` — one call, one `$group` aggregation by `{year, month, type}` over the whole trend range. Returns **both** `income` and `expense` per month (`MonthlyTrendRawPoint`) instead of a single `metric`-filtered `value`, specifically so toggling the Pengeluaran/Pemasukan tab (`MonthlyTrendChart`'s `onMetricChange`) is a pure client-side re-render (`useReports`'s `monthlyTrend` is a `useMemo` over the raw fetch) — it never needs a refetch.
- `useReports` still keeps one raw `queryTransactions({ dateFrom, dateTo })` call (`periodTransactions`) — that's the only thing left that genuinely needs an itemized list: the export's transaction-list section (`incomeExpenseTransactions`). Cash flow no longer needs it.
- `api-docs.ts`'s "report" group: `report-summary`, `report-wallet-usage`, `report-top-spending`, `report-cash-flow`, and `report-monthly-trend` are all real now (real `{isSuccess}` envelope, matching actual response shape). Only `report-category-breakdown` (bundled into `report-summary`'s response instead of its own endpoint) and `export-report` (export generation is entirely client-side — the real "endpoint" would just be a filename formatter, not a real file-producing route) were never built and stay aspirational (`{success}` envelope) — don't "fix" those until they're actually built.

### The core pattern — follow it for every new data-owning feature

Every entity (wallet, category, transaction, settings, auth) is wired the same five-part way. When adding a new feature that owns data, replicate all five parts — skipping the api-docs entry or the service seam is the most common way this codebase drifts out of "backend-ready":

1. **Type** — `src/types/<entity>.types.ts`: the entity shape plus an `Input` type for create/update payloads (e.g. `TransactionInput = Omit<Transaction, "idTransaction">`).
2. **Service** — `src/services/<entity>.service.ts`: async functions that `await delay()` and read/write an in-memory mock array (`src/constants/mock-*.ts`). This is the seam where real `fetch()` calls get dropped in later — no component or hook should touch mock data directly.
3. **Redux slice** — `src/redux/slices/<entity>Slice/index.ts`: holds the entity list/object plus a `status: "idle" | "loading" | "loaded"` field, with reducers like `set<Entity>Loading`, `set<Entity>`, `add<Entity>`, `update<Entity>`, `remove<Entity>`. Re-export from `src/redux/slices/index.ts`. (The oldest slice, `authenticationSlice`, uses `onLogin`/`onLogout`/`onSetToken` naming instead — new slices should follow the newer `set*`/`add*`/`update*`/`remove*` convention, not that one.)
4. **Hook** — `src/hooks/use-<entities>.ts`: composes service + slice (`load<Entities>` dispatches loading then the service result; mutating methods call the service then dispatch the result). Components never call services or dispatch slice actions directly — always through the hook.
5. **API doc entry** — add the endpoint (method, path, payload fields, success/error JSON examples) to the matching group in `src/constants/api-docs.ts`, and add an `apiDoc.groups.<key>` string to all three `src/helpers/lang/*.json` files.

Reference implementation to copy from, for a still-mocked entity: settings (`settings.types.ts` → `settings.service.ts` → `settingsSlice` → `use-settings.ts` → "settings" group in api-docs.ts). For a richer, now-real entity showing how a `type`-discriminated payload works: transaction — `Transaction.type` is `"income" | "expense" | "transfer" | "correction"`, and `idWallet`/`idCategory`/`idSubCategory`/`idWalletFrom`/`idWalletTo` are all nullable because which ones apply depends on `type` (transfer uses `idWalletFrom`/`idWalletTo` instead of `idWallet`; transfer/correction have no category) — but note its wallet-balance/category-count side effects are now computed **backend-side**, not in `use-transactions.ts` (see above), so it's not a template for how a still-mocked entity's hook should look.

### Account domain (danger-zone reset)

Settings → "Zona Berbahaya" → Reset Data is wired to a real backend endpoint, `DELETE /account/data` (`src/services/account.service.ts`), which wipes every wallet/category/transaction/instrument/investment-transaction document owned by the logged-in user in `tosm-fi-be`'s database — not just the local Redux cache. `src/hooks/use-reset-data.ts`'s `resetData()` is now async: it calls `accountService.resetData()` first, then (only on success) dispatches the existing `resetAccountData(dispatch)` Redux-clear so local state matches the now-empty server. `resetAccountData` itself is unchanged and still shared with the logout paths (`use-auth.ts`, `use-session-bootstrap.ts`, `http-client.ts`'s auto-logout interceptor) — those paths must never call the delete endpoint, they only need to clear the local cache for the next account that logs in. `SettingsPage`'s `handleResetData` awaits `resetData()` inside a try/catch and shows an error toast (`settingsDanger.resetError`) if the request fails, instead of assuming success. `api-docs.ts`'s new "account" group documents this endpoint with the real `{isSuccess}` envelope.

### Client error log domain (crash reporting → admin-only Settings view)

`src/utils/crash-logger.ts`'s `logCrash()` — called by `ErrorBoundary` (render crashes) and `global-error-logging.ts` (`window.onerror`/`unhandledrejection`) — does `console.error` as before, then also fire-and-forgets a report to the real backend via `clientErrorService.reportError()` (`POST /errors`, `src/services/client-error.service.ts`). The `.catch(() => {})` on that call is load-bearing: reporting a crash must never itself throw, since the console.error above is the only fallback if the network/API is down. `logCrash`'s existing `details` bag is destructured into `message`/`stack` (typed fields) plus whatever's left over (e.g. `componentStack` for render errors, `filename`/`line`/`column` for `window.onerror`) bundled into a generic `extra` object — this let the backend schema stay flexible without every crash source needing its own dedicated fields.
- Settings → "Log Error" (`src/app/pages/SettingsErrorLogPage`, admin-only, gated the same way as `SettingsUserApprovalPage` — a `user.role !== "admin"` check that `<Navigate>`s back to `/settings`) lists every reported crash across every user via `GET /errors`, newest first, backend-capped at 200 rows since this is a diagnostic tool, not a paginated data view.
- `clientErrorSlice` follows the same "admin-only view, always refetched, never persisted" treatment as `userApprovalSlice` — not added to `store.ts`'s persist `whitelist`. `removeClientError` is a plain local-array filter (no re-fetch) since the backend's `DELETE /errors/:idClientError` doesn't return the remaining list.
- `POST /errors` only requires the backend's `requireAuth` (not `requireActiveUser`) — a pending user's crash should still be captured. There's currently no path for reporting a crash that happens before any login at all (e.g. on `/login` itself) since every crash-reporting call site assumes a token exists; that's an accepted gap, not a bug, since virtually all app crashes happen behind `ProtectedRoute` where a token is guaranteed.
- `crash-logger.ts` tags every report with `environment: import.meta.env.DEV ? "development" : "production"` — Vite's own build-mode flag for the frontend bundle that was actually running, not the backend's `NODE_ENV`. `SettingsErrorLogPage` renders this as a badge and as a filter chip (All/Development/Production).
- `GET /errors` accepts optional `search`/`environment`/`source` query params, all passed straight through as `httpClient.get("/errors", { params })` — `SettingsErrorLogPage` debounces `search` (`SEARCH_DEBOUNCE_MS`, same render-time-reset-free pattern as other search inputs, just simpler since this list isn't paginated) and refetches whenever either filter changes.
- `isRead` badge ("Baru"/"New"): the backend flips a row's `isRead` to `true` server-side the moment it's included in a `GET /errors` response, but that same response still reports the pre-flip value — so `SettingsErrorLogPage` only ever needs to render `!item.isRead` from whatever the last fetch returned, it never manages read/unread state itself. Revisiting the page (or changing a filter, which refetches) always shows previously-seen rows as read.
- `username` is resolved server-side (a batch lookup against `UserModel` by the distinct `idUser`s in the current page of results) and returned directly on each `ClientError` — the frontend never fetches or joins against a separate user list for this.
- Delete: `SettingsErrorLogPage`'s per-row trash button goes through the same `useConfirmDialog` + `useToast` pattern as `SettingsPage`'s danger-zone reset (destructive confirm, error toast on failure) before calling `deleteClientError`, which calls `DELETE /errors/:idClientError` then removes the row from `clientErrorSlice` locally.
- `api-docs.ts`'s new "clientError" group documents all three endpoints (`POST /`, `GET /` with its filter params, `DELETE /:idClientError`) with the real `{isSuccess}` envelope.

### Redux persistence and the settings exception

`src/redux/store.ts` combines all slices into one `persistReducer` with a single `whitelist` array — there is no per-slice persist config. When adding a slice that should survive reloads, add its key to that `whitelist`.

For slices backed by a real API (`wallet`, `category`), a `createTransform` resets `status` back to `"idle"` on every rehydrate — otherwise a persisted `"loaded"` status would make every consumer's `if (status === "idle") load…()` guard skip refetching after a reload, showing indefinitely-stale data (a previous account's data, or changes made directly via the API). Add the same transform for a slice once its backend goes real.

`settingsSlice` (currency, decimal places, language) is the one place this gets subtle: `src/helpers/i18n.ts` calls `i18n.init()` at module-load time, before React (and therefore Redux/`PersistGate`) has mounted, so it can't read the persisted Redux state yet. It reads a raw `localStorage` key (`LANG_STORAGE_KEY`) directly instead. `src/services/settings.service.ts` writes to that same raw key whenever `language` changes, in addition to the normal Redux round-trip, so the next page load's `i18n.init()` sees the current language before Redux rehydrates. `useCurrency()` and `useLanguage()` are both thin wrappers around `useSettings()` that preserve their pre-Redux public API (`{ currency, setCurrency, decimalPlaces, setDecimalPlaces, format }` / `{ language, changeLanguage }`) — no consumer needed to change when these moved off plain `localStorage`.

Preferences that are genuinely local-only and not meant to sync to a future backend (theme light/dark, wallet grid/list view mode) intentionally stay outside Redux, reading/writing `localStorage` directly via their own hook (`use-theme.tsx`, `use-wallet-view-mode.ts`).

### Component layers

- `src/components/atoms/`, `molecules/`, `organisms/`, `templates/` — generic, feature-agnostic UI primitives (atomic design). `Words` is the text primitive (use it instead of raw `<p>`/`<span>` for anything user-facing so type scale/weight stay consistent); `Modal` is the shared dialog shell every feature modal wraps.
- `src/layouts/<feature>/` — composite, feature-specific components (e.g. `layouts/transaction/AddTransactionModal`, `layouts/wallet/BalanceCorrectionModal`). This is where most feature work happens; `src/app/pages/*Page` components stay thin and mostly just wire hooks to layout components.
- Amount entry (calculator-style keypad with `+ - × ÷`, keyboard input, and an expression preview) is shared via `src/hooks/use-amount-calculator.ts` + `src/components/molecules/AmountCalculatorKeypad`, reused by both `AmountCalculatorModal` (transaction amount) and `BalanceCorrectionModal` (new balance).

### Routing and auth gating

Routes are centralized in `src/constants/routes.ts` (`ROUTES`) and wired in `src/app/AppRouter/index.tsx`. Every route except `/login` is wrapped in `src/app/ProtectedRoute/index.tsx`, which redirects to `/login` when `useAuth().isAuthenticated` is false — there's no route-level code splitting or nested layouts beyond that single gate.

### Styling

Tailwind v4, configured entirely in CSS (`src/css/index.css`) via `@theme` — there is no `tailwind.config.js`. Custom color tokens (`primary-*`, `ink-*`) and the font face are defined there. Dark mode is a class variant (`@custom-variant dark (&:where(.dark, .dark *))`) toggled by `use-theme.tsx` adding/removing a `.dark` class, not a media query — always pair `dark:` classes rather than relying on `prefers-color-scheme`.

### i18n

Three languages — `id` (default/fallback), `en`, `jp` — as flat-key JSON files in `src/helpers/lang/`. Every user-facing string goes through `useTranslation()`'s `t()`; when adding a string, add the same key to all three files in the same position (existing files are kept in sync key-for-key, not just per-language supersets).

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
